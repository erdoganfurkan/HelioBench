## Known issues found while producing this run, not fixed here

- **`n1_mms_fgm` invented-id bug** — the detector fires and warns, but the agent loop ends instead of retrying with the real ids. Logged in HelioAI's memory: `bug-unknown-ids-no-retry-2026-08-19`.
- **Sandbox disk cost** — `_seed_speasy_inventory` copies whatever `$XDG_DATA_HOME/speasy` resolves to. On the shell used to drive this benchmark (VS Code snap), that pointed at an unrelated 611MB cache instead of the normal ~35MB one, filling the disk mid-run twice. Not a HelioAI bug — the fix (81202ea/f49c25e) works correctly; this was an environment artifact of the driving shell. Worked around by pinning `XDG_DATA_HOME` explicitly before `heliobench run`.
- **Azure daily quota (2M tokens/day)** — hit mid-sweep on the first n1 attempt (30 tasks × 3 runs). The 4 cut tasks were re-run cleanly the next day once the quota reset.

## Correction (2026-08-21) — three defective n1 answer keys

Auditing the failures against the search index itself, rather than against the key, showed
that three of the five n1 failures above are defects in the benchmark. Every identifier the
agent gave was checked in the index it searched (`speasy_catalog`, 82,433 entries); all but
`n1_mms_fgm`'s exist.

| Task | Published verdict | What the index says | Fix applied |
|---|---|---|---|
| `n1_wind_position` | 0/3, agent failure | the agent's `cda/WI_H0_MFI/PGSE` is *"Position vector in GSE coordinates (Define Re = 6378km) (1 min)"* — 15 entries answer the prompt as written, the key listed 2 | **key widened** to all 15; prompt unchanged |
| `n1_amda_imf` | 0/3, agent failure | three AMDA products carry an IMF vector in GSE: `amda/imf` (16 s, CDAWeb), `amda/imf_real_gse` (60 s real-time, NOAA), `amda/dsc_b_gse` (DSCOVR). The prompt separated none of them | **prompt hardened** to name definitive CDAWeb data; key unchanged. Telling definitive from real-time is a skill worth testing, so this is not widened |
| `n1_themis_fgm` | 0/3, agent failure | the agent's `cda/THA_L2_FIT/tha_fgs_gsm` is *"FGS (spin-fit) magnetic field vector in GSM coordinates"* from THEMIS-A's *"On Board spin fits of … Magnetic (FGM) field"* — indistinguishable from the key under the prompt as written | **prompt hardened** to name the L2 FGM dataset; key widened to all eight GSM vectors inside it |
| `n1_dst_index` | 2/3 | run 2 answered `cda/MMS1_MEC_BRST_L2_EPHT89D/mms1_mec_dst`, runs 0–1 answered `amda/dst` | no change — a genuine agent wobble |
| `n1_mms_fgm` | 0/3, invented ids | confirmed: the ids are absent from the index, deterministic across all 3 runs | no change — a genuine agent bug, since fixed in HelioAI |

Accepted ids are now enumerated from the index by `scripts/n1_key_candidates.py`, and each
task's `provenance` records the query that produced them.

### What the corrected number is

Re-grading the stored traces with the corrected keys — deterministic, no new API calls:

| | Runs | Rate |
|---|---|---|
| Published n1 figure | 77/90 | ~85.6% |
| Re-graded, 28 tasks whose prompt did not change | **80/84** | **95.2%** |
| `n1_amda_imf`, `n1_themis_fgm` | unscored | prompt changed — the old runs answered a different question |

The two hardened tasks are deliberately *not* re-scored from the old traces: the agent never
saw the new wording, and scoring it against a question it was not asked would repeat the
mistake this correction is fixing. They need a re-run.

`task_set_digest` changed with them: n1 went from `a6a091263540b2ad` to `bbd80de619d6d136`,
the full 58-task set to `5d57856c61028545`. Scores under different digests are not
comparable, which is exactly what the digest is for.

### The rule this closed

**A task is defective when a defensible answer exists that its key rejects.** The measured
consequence: on this run the benchmark was wrong more often than the agent was — 3 broken
tasks against 2 genuine failures. See `docs/what-this-measures.md`.

### A fourth defective key, found by the same rule

`n1_dst_index` asked *"which archived product provides the Dst geomagnetic index?"* — and 27
entries in the index provide one. Twenty-four are the same index copied into an MMS MEC
ephemeris dataset, described as *"Dst index from QinDenton files. Used as input to magnetic
field models."* Those were defensible answers that the key rejected, which by the rule in
`docs/what-this-measures.md` makes the task defective, not the agent wrong.

The prompt now asks for the index itself rather than a copy carried as a model input, and the
key accepts `amda/dst` and `amda/omni_dst`. The agent passed 1 of 3 runs afterwards, so this
was not a change that made the task easier — it made it answerable.

### How the sweep was actually run

It died at run 69 of 90 with the disk full: the leftovers of earlier sweeps, ~37 MB of seeded
workspace per tier-n3 session, and the failure surfaced as a sqlite error inside the agent
loop rather than as anything about storage. The remaining tasks were run afterwards, the
traces merged into one directory, and every one of the 90 re-graded together by
`heliobench report --regrade` — deterministic, no second call to a provider. `verify` now
refuses to start under 2 GB free.
